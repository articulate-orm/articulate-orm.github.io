Run entity methods around persistence, update, removal, and hydration events.

## Attributes

```php
#[PrePersist]
public function onPrePersist(): void
{
}

#[PostPersist]
public function onPostPersist(): void
{
}
```

## Use cases

<CardGrid>
	<Card title="Timestamps" icon="pencil">
		Set `created_at` in `#[PrePersist]` and `updated_at` in `#[PreUpdate]`. There is no built-in auto-timestamp attribute — this is done by hand in the callback, as in the example below.
	</Card>
	<Card title="Auditing" icon="pencil">
		Write an audit-log record in `#[PostPersist]` / `#[PostUpdate]` / `#[PostRemove]`, once the write is known to have succeeded.
	</Card>
	<Card title="Validation" icon="pencil">
		Reject invalid state in `#[PrePersist]` / `#[PreUpdate]` by throwing — the throw prevents the write (see pitfalls below).
	</Card>
	<Card title="Normalization" icon="pencil">
		Trim, cast, or recompute derived fields in `#[PostLoad]` right after hydration, so every code path sees the same shape.
	</Card>
	<Card title="Soft-delete bookkeeping" icon="pencil">
		Stamp the soft-delete marker in `#[PreRemove]` for entities that don't rely solely on `#[SoftDeleteable]`'s own handling.
	</Card>
</CardGrid>

```php
#[PreUpdate]
public function onPreUpdate(): void
{
    $this->updated_at = self::now();
}

#[PostLoad]
public function onPostLoad(): void
{
    $this->record('PostLoad');
}
```

## Common pitfalls

<Aside type="caution">
- Throwing from `PrePersist` prevents the entity from being written.
- `PostLoad` can run on `find()`, query-builder hydration, **and** explicit relation loading — don't assume it only fires once per object lifetime.
- Keep callback side effects narrow so command/request output stays understandable.
</Aside>

Articulate has three independent cache layers, all using PSR-6 (`CacheItemPoolInterface`). Pass the same pool instance to share backend, or separate instances for isolation.

## Second-level cache

Cross-request entity cache. Survives beyond a single `EntityManager` instance.

```text
Request A: identity map miss → DB hit → entity stored in L2 cache
Request B: identity map miss → L2 cache hit → DB skipped entirely
Request C: identity map miss → L2 cache hit → DB skipped entirely
```

```php
$em = new EntityManager(
    $connection,
    secondLevelCache: $entityPool,
    secondLevelCacheTtl: 3600,
);
```

`secondLevelCache:` is the only switch: `resultCache:` alone never caches `find()`. Both options may point at the same pool. Ids are normalized to the primary-key property's type, so `find(User::class, '1')` and `find(User::class, 1)` share one entry.

`find()` checks the identity map first, then the L2 cache, then the database. On `flush()`, modified and deleted entity entries are evicted automatically — stale data is never served after a write. Eviction also covers **sibling** entity classes sharing the same table and primary key.

### Cacheable queries

`find()` uses the L2 cache automatically. Query-builder lists opt in per query with `cacheable(?int $ttl = null, array $dependsOn = [])`:

```php
$users = $em->createQueryBuilder(User::class)
    ->where('status', 'active')
    ->orderBy('id')
    ->cacheable()          // TTL defaults to secondLevelCacheTtl (3600s)
    ->getResult();
```

- **Caches the id list, not rows.** The ordered primary keys of the **root table** (the table of the hydrated entity) are stored; on a hit each id is resolved from the identity map or the per-entity L2 cache. If any id can't be resolved that way, the whole query re-runs against the database. Row data is never duplicated between the two caches.
- **Silent no-op when not applicable.** Only applies when `getResult()` hydrates full entities with the default `ObjectHydrator` and the entity has a single-column primary key. Aggregates, specific-column selects, custom hydrators and `lock()` queries run uncached. Without a second-level cache configured on the manager, `cacheable()` does nothing.
- **`chunk()` just works.** Each page has its own `limit`/`offset` and is cached as its own id list.

#### Invalidation: table generations

Every database table has one **table generation** counter in the cache pool. A cached list's key includes the generation of its root table and of every **dependency table** — any other table the query reads. `flush()` bumps the generation of every table it wrote, once per table however many rows changed: inserts, entity updates, merged sibling updates, hard and soft deletes, and many-to-many mapping (pivot) rows written by the unit of work. After a bump the old key no longer matches, the next read misses and re-queries, and the old list ages out via its TTL.

That covers the cases row-level invalidation can't:

- **Joins.** `join`, `leftJoin`, `rightJoin` and `crossJoin` targets are dependency tables. Aliases (`posts p`) resolve to the real table name; a self-join of the root table counts once.
- **Subqueries.** Tables read by a `QueryBuilder` passed to `whereExists()`, `orWhereExists()` or `whereIn()` are dependency tables — recursively, including joins and subqueries nested inside them.
- **Rows moving into or out of a predicate.** An `UPDATE` that makes a row newly match (or stop matching) the `WHERE` clause bumps the root table, so the list is re-queried.
- **Sibling slices.** All slices of a table share its generation, so a write through `AdminUser` invalidates a list cached through `LoginUser`.
- **Other `EntityManager`s.** Generations live in the shared pool: a flush in one context invalidates lists every context reads from that pool.

Writes to tables a query does not read leave its list a hit.

**Declare what the builder can't see.** Tables referenced only inside `whereRaw()`, raw join conditions or raw SQL are not detected. Name them with `dependsOn` (table names, not entity classes):

```php
$posts = $em->createQueryBuilder(Post::class)
    ->whereRaw('EXISTS (SELECT 1 FROM post_tags pt WHERE pt.post_id = posts.id)')
    ->cacheable(dependsOn: ['post_tags'])
    ->getResult();
```

Declared tables are merged with the detected ones and deduplicated, so over-declaring — including a table the query already joins — is harmless.

**The trade-off is hit rate.** Any unit-of-work write to a table evicts every cached list that reads it, related to the changed row or not. `cacheable()` pays off for lists over tables that are read far more often than written. Cost per `cacheable()` query: one batched `getItems()` for the root and dependency generations, alongside the id-list read.

**Bump timing.** When `flush()` owns the transaction, the bump runs after `COMMIT`, so a concurrent reader can't re-cache pre-commit state under the new generation. When `flush()` runs inside a caller-owned transaction (including `transactional()`), the bump runs at the end of `flush()`, before the caller commits: another process can cache the pre-commit list under the new generation in that window, and it stays stale until TTL.

**Fail-open.** Cache backend errors fall back to a database query. If any involved table's generation can't be read, that call skips the cache entirely — no read, no write — because a list stored under an unknown generation could never be invalidated. A bump that fails during an outage leaves pre-change lists matchable after recovery, until TTL.

<Aside type="caution">
	Writes outside the unit of work — `QueryBuilder` `update()`/`delete()`/`insert()` and raw SQL — never bump a generation. Lists reading those tables stay stale until TTL. Invalidate by writing through `flush()`, keep TTLs short, or don't use `cacheable()` on those tables. See [Known Limitations](/guides/known-limitations/#caching).
</Aside>

Design rationale: [ADR 0003](/reference/adr-0003-collection-cache-table-generation-invalidation/), which supersedes the row-level design in [ADR 0002](/reference/adr-0002-collection-second-level-cache/).

`cacheable()` is unrelated to `enableResultCache()` below: the result cache stores raw SQL rows by SQL text and is invalidated wholesale on every flush.

## Query result cache

Cache raw result sets from `QueryBuilder` queries — useful for read-heavy queries that don't change often.

```php
$users = $em->createQueryBuilder(User::class)
    ->from('users')
    ->where('status', 'active')
    ->enableResultCache(lifetime: 300, resultCacheId: 'active_users')
    ->getResult();
```

- Custom cache key via `resultCacheId`, or auto-generated from query shape + parameters.
- Locked queries (`FOR UPDATE`) are never cached.
- Call `disableResultCache()` to opt out per query.

## Statement cache

Caches compiled SQL strings (query structure, not results) — eliminates repeated SQL compilation for queries with the same shape but different parameter values.

```php
$em = new EntityManager($connection, statementCache: $cachePool);
```

Transparent — no per-query opt-in needed. Failures are silently ignored so a broken cache backend never breaks queries.
